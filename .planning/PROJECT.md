# Система продажи билетов через VK бота

## What This Is

Система управления продажей билетов на концерт для команды билетеров через VK бота. Билетеры пересылают боту сообщения клиентов для создания броней, управляют местами (добавление/удаление), регистрируют оплату и получают готовые скрипты для отправки клиентам. Админы дополнительно управляют резервами с комментариями и видят общую статистику. Вся занятость мест хранится в единой базе с атомарными транзакциями для предотвращения конфликтов.

## Core Value

**Ни одно место не может быть продано дважды.** Все операции с местами атомарны, уникальность занятости гарантируется partial index на уровне БД, конфликты выявляются до коммита транзакции.

### Out of Scope

- Веб-интерфейс для билетеров — все операции только через VK бота
- Автоматическая оплата через VK Pay API — регистрация оплаты вручную билетером
- Выбор конкретных мест при частичной оплате — используется детерминированный порядок (row ASC, seat ASC)
- Редактирование резервов обычными билетерами — только админы могут управлять резервами
- Множественные активные брони на одного клиента — строго одна активная бронь

## Context

**Существующая инфраструктура:**
- База данных уже спроектирована и реализована на SQLAlchemy 2.0+
- Модели покрывают все сущности: пользователи (VK + внутренние), брони, места, платежи, audit log
- SQLite для MVP, миграция на PostgreSQL запланирована при масштабировании
- Тесты базы данных написаны (test_db.py), покрывают основные сценарии

**VK бот — новая разработка:**
- Библиотека: vkbottle (async, встроенная FSM)
- Состояние сессий: Redis (permanent storage, очистка только явная)
- Основной паттерн: пересылка сообщения клиента = выбор покупателя + главное меню
- Детальная спецификация: `.planning/BOT_SPEC.md`

**Бизнес-правила:**
- Один клиент = одна активная бронь
- Места вводятся через пробел, запятые или диапазон (5-7)
- Комментарии только для резервов (обязательны)
- Скрипт для клиента отправляется после создания/редактирования брони
- Должники: клиенты без оплат >= 7 дней

**Известные проблемы (из CONCERNS.md):**
- Incomplete audit log action type catalog — нужно финализировать для бота
- Missing payment reversal mechanism — нужно решить (отдельная таблица vs audit log)
- No concurrency testing — критично протестировать перед запуском
- SQLite concurrency limit — миграция на PostgreSQL при >10 одновременных билетеров

## Constraints

- **Технический стек**: Python 3.14+, vkbottle, Redis, SQLAlchemy 2.0+, SQLite → PostgreSQL
- **VK API**: Ограничение на количество запросов (нужен rate limiting в боте)
- **Время разработки**: ~61-77 часов по оценке (6 фаз)
- **Конкурентность**: SQLite поддерживает только одного писателя — миграция на PostgreSQL критична при масштабировании
- **Макет зала**: Фиксированный 24 ряда × 28 мест, загружается из JSON при старте бота

## Key Decisions

| Decision | Rationale | Outcome |
|----------|-----------|---------|
| vkbottle вместо aiogram | aiogram только для Telegram, vkbottle специально для VK с встроенной FSM | ✓ Good — подходит для требований |
| Redis для FSM состояния | Permanent storage без TTL, очистка только явная | — Pending — нужно протестировать |
| Детерминированная частичная оплата | Простота реализации, предсказуемость для билетеров (row ASC, seat ASC) | — Pending — может потребоваться ручной выбор |
| SeatAssignment.note только для резервов | Комментарии нужны только админам для пояснения резервов | ✓ Good — упрощает модель |
| Скрипт после брони, не после оплаты | Билетер отправляет скрипт сразу после бронирования для подтверждения | — Pending — уточнить workflow |
| Один клиент = одна бронь | Упрощает логику, предотвращает путаницу | ✓ Good — соответствует бизнес-процессу |
