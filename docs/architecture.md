# Архитектура

Правила устройства кода. Коротко о проекте — в [README](../README.md), эксплуатация сервера — в [operations.md](operations.md), исходное ТЗ — в [TZ.md](TZ.md).

## Структура

```
src/tickets/
  config.py     настройки (pydantic-settings), секции проверяются при первом обращении
  logging.py    setup_logging()
  time.py       aware UTC: utcnow(), from_unix()
  db.py         engine, фабрики сессий, unit_of_work(), миграции из кода
  hall.py       геометрия зала из layout.json
  notify.py     notify_owner(): сообщения и файлы владельцам в VK
  formatting.py склонения, диапазоны мест «1-3, 5»
  models/       ORM-модели и все enum'ы предметной области
  services/     users, reservations, seats, payments, reports, audit, errors
  bot/          main, router, flows/, fsm/, vk.py, auth.py, keyboards, texts
  web/          main.py, deps.py, routers/, filters.py, templates/
  jobs/         backup, debtors, runner, crontab
migrations/     Alembic
tests/          unit/, integration/, test_guards.py, test_config_guards.py
```

Запуск: `python -m tickets.bot`, `uvicorn tickets.web.main:app`, `python -m tickets.jobs.backup`, `python -m tickets.jobs.debtors`.

## Правила зависимостей

```
bot, web, jobs         ← интерфейсы: ввод → сервисы → ответ
      ↓
services               ← бизнес-правила
      ↓
models, db, hall       ← данные
      ↓
config, logging, time  ← ни от чего не зависят
```

- Веб и задачи не импортируют ничего из `bot/`.
- Между сервисами без циклов: `payments`, `reports` → `reservations` → `seats`, `users` → `audit`. Цикл — сигнал опустить общую часть ниже. Общего `utils.py` для бизнес-логики нет.

## Сервисы

- Модули с `async`-функциями, `session` (`AsyncSession`) — первый аргумент. Без слоя репозиториев: SQLAlchemy напрямую.
- Переиспользование: внутри сервиса — приватные функции модуля; между сервисами — вызов публичной функции в той же сессии. Общая функция живёт в сервисе своей сущности («освободить места» — `seats`).
- Сервисы ничего не знают о VK: получают обычные значения, а не объект сообщения vkbottle.
- Ошибки предметной области — `services.errors` (`ServiceError` и наследники); интерфейсы переводят их в ответ пользователю.

## Транзакции

- Сервисы **никогда** не вызывают `commit()` / `rollback()`; для получения `id` — `session.flush()`. Страж — `tests/test_guards.py`.
- Транзакцию открывает и завершает граница: `async with unit_of_work() as session:` в сценарии бота и в задаче; в вебе — зависимость на запрос (`Depends(..., scope="function")`, чтобы коммит был до ответа). Успех → COMMIT, исключение → ROLLBACK.
- Внутри транзакции нет сетевых вызовов: сначала данные из VK, потом короткая транзакция, потом ответ. Побочные эффекты (сообщения VK, `notify_owner`, файлы) — только после коммита.
- Всё, что меняет бронь, сначала берёт её под блокировку (`reservations.lock_active`, `SELECT … FOR UPDATE`) и проверяет, что она активна: параллельные изменения одной брони выполняются по очереди.
- Двойное занятие места невозможно на уровне базы: частичный уникальный индекс по `(row_number, seat_number) WHERE released_at IS NULL`. Сервис сначала проверяет конфликты (понятный ответ), затем вставляет в SAVEPOINT; гонка на индексе превращается в `SeatOccupiedError`, а не в ошибку базы.
- Аудит (`audit_log`) пишется в той же транзакции, что и изменение.

## Конфиг

- `pydantic-settings`, все настройки в `config.py`, нигде больше нет `os.getenv`. Умолчания в коде — только несекретное и одинаковое везде (`LOG_LEVEL=INFO`, `DISPLAY_TZ=Europe/Moscow`, …). Секреты — `SecretStr`, обязательные и непустые: без них процесс не стартует.
- Приоритет: окружение → `.env` → файлы секретов (`/run/secrets/<поле>`, `./secrets/<поле>`) → умолчание.
- Константы предметной области (геометрия зала, тексты бота) — не конфиг.

## Даты

- В коде везде aware UTC (`tickets.time.utcnow()`, `from_unix()` для дат VK), в базе — `timestamptz`. Бизнес-логика («N дней без активности») — только в UTC.
- В `DISPLAY_TZ` (Europe/Moscow) переводится только при показе: Jinja-фильтр `local_dt`, форматирование в боте. Расписание `cron` — по Москве (`CRON_TZ`).

## Бот

- `router.py` регистрирует обработчики по порядку (vkbottle берёт первое совпадение): управление пользователями → сообщение о покупателе (пересылка, ответ, ссылка на профиль) → команды → обработчики состояний FSM.
- `flows/` — сценарии диалога; зарегистрированная функция и есть вход в сценарий, отдельного слоя `handlers/` нет. Данные — только через сервисы в `unit_of_work`.
- `vk.py` — всё, что связано с VK: разбор входящего, имя через VK API, отправка только через `answer()` / `send()` с уникальным `random_id` (VK отбрасывает повтор при ретрае).
- `auth.py` — права декораторами: `requires_registered`, `requires_admin`, `owner_only`, `guard_state`.
- Источник событий — Long Poll; Callback API — в [роадмапе](roadmap.md).

## FSM

- Состояние и контекст — в Redis, без TTL. Контекст — pydantic-модели (`Client`, `PendingSwitch`, `SavedState`, …), состояния — `BotState`.
- Каждый шаг с бронью проверяет через сервис, что бронь существует и активна; иначе — сообщение билетёру и сброс.

## Веб

```
web/
  main.py      приложение; обработчик 500 → лог + notify_owner
  deps.py      сессия (unit of work на запрос), проверка входа админа, client_ip
  routers/     public (/), concert_day, payments, health
  filters.py   время в DISPLAY_TZ, деньги, диапазоны мест
  templates/   Jinja (SSR)
```

Роуты тонкие: данные — из сервисов `reports` и `payments`, подготовка для шаблона — в роуте. Внешние скрипты — с точной версией и SRI.

## Уведомления владельцу

- `notify_owner(text, file=None)` — владельцам из `OWNER_VK_IDS` через VK API с токеном сообщества, из любого процесса, без запущенного бота. Никогда не бросает исключений.
- Вызывают только интерфейсные слои: обёртка задач (падение, файл бэкапа), обработчик ошибок бота, обработчик 500 в вебе.
- Одинаковые ошибки (`dedup_key`) — не чаще раза в 10 минут, в памяти процесса.

## Миграции и совместимость

- **Expand/contract:** каждая миграция совместима с предыдущей версией кода. Новая колонка — nullable или с `server_default`. Переименование — новая колонка, запись в обе, перенос данных, переключение чтения; старая удаляется через релиз. Удаление колонки — только после релиза, где код её не использует. `NOT NULL` — после заполнения данных.
- **Contract-миграции** (удаление, `NOT NULL`, сужение CHECK) явно помечаются и выходят на релиз позже кода, который перестал от них зависеть.
- **Только вперёд:** откат = откат кода, база остаётся. Downgrade-миграции пишем, но в проде не используем. При проблеме по возможности чиним вперёд.
- **Страховка:** `db-backup` (`pg_dump`) перед каждым `migrate`, если есть ненакатанные миграции.
- **Enum в VARCHAR + CHECK:** новое значение — сначала код умеет его читать и CHECK расширен, в следующем релизе код начинает его писать. Удаление — наоборот: перестать писать → перенести данные → сузить CHECK. Autogenerate не видит CHECK — такие миграции пишутся руками, `tests/integration/test_migrations.py` падает, пока миграции нет.
- **Миграции не импортируют модели и enum'ы** (`op`, `sa.table()` и литералы): старая миграция должна работать на пустой базе и после изменения моделей.
- **FSM-контекст (без миграций), схема при чтении:** новые поля только с умолчаниями; `extra="ignore"` — старый код игнорирует новые поля; поле версии `v` — для будущих несовместимых изменений. Ошибка чтения → лог, сброс, «начните заново» — никогда не падение.
- **Краевые случаи:** старый код работает с новой схемой во время деплоя (поэтому expand/contract нужен и без откатов); Postgres выполняет миграцию в транзакции, кроме `CREATE INDEX CONCURRENTLY`; миграции данных — отдельно от схемы и идемпотентны.

## Бэкапы

- Одна задача `tickets.jobs.backup`, два повода: `cron` раз в день с отправкой владельцу в VK (отключается `BACKUP_SEND_TO_VK=false`) и сервис `db-backup` перед `migrate` (`--reason pre-migrate`, без отправки).
- `pg_dump -Fc`, восстановление через `pg_restore` ([operations.md](operations.md)). Хранение — `./backups`, ротация: последние 14 каждого вида.
- Не делаем: шифрование, S3, WAL / point-in-time recovery. Дамп содержит персональные данные — уходит только владельцу.

## Секреты и доступы

- **Секреты приложения:** Compose `secrets:` — файлы в `secrets/` (в `.gitignore`), монтируются в `/run/secrets/<имя>`, каждому сервису — только нужные. Postgres — `POSTGRES_PASSWORD_FILE`, Redis получает конфиг с паролем через stdin (пароля нет в аргументах процесса). На сервер кладутся вручную один раз; CI их не получает. Несекретные настройки сервера — в `.env`.
- **Доступы:**
  - сервер → GitHub: deploy key только на чтение;
  - GitHub Actions → сервер (с CI, шаг 2): отдельная пара ключей; приватный ключ и `known_hosts` — в GitHub Secrets; публичный — в `authorized_keys` с `command="…"` (только деплой-скрипт), `no-pty`, `no-port-forwarding`;
  - сервер → GHCR (с CI, шаг 2): токен с `read:packages`.

## Тесты

- `tests/unit/` — без базы, Redis и сети, Docker не нужен (`uv run pytest tests/unit`). `tests/integration/` — сервисы на Postgres, FSM на Redis, сценарии бота с подменённым VK, веб-роуты через `httpx`, миграции. `tests/test_guards.py`, `tests/test_config_guards.py` — правила кода и согласованность `compose.yaml` с кодом.
- Postgres и Redis — testcontainers, те же образы и локаль базы, что в Compose. Схема — `alembic upgrade head`; изоляция — `TRUNCATE … RESTART IDENTITY` перед тестом, а не откат транзакции: код коммитит сам, а тесты конкурентности нуждаются в нескольких настоящих транзакциях.
- `pytest-cov` без порога: `uv run pytest --cov`.
