# ТЗ: учет билетов на студенческий концерт (операции и интерфейсы)

## 1) Контекст и цель

Нужно автоматизировать учет мест в зрительном зале для **одного** концерта на **одной** площадке с **одной** расстановкой мест.

Продажи происходят через людей (**билетеров**) — основной рабочий интерфейс для них: **VK-бот**. Покупателю нужен только визуал зала (без покупки/кликов).

Фокус этого документа: **функции, операции, пользовательские флоу и интерфейсы**.  
Модель данных/таблицы БД — позже, т.к. ожидаются изменения.

## 2) Термины

- **Место**: пара (ряд, номер места). Валидность места определяется ограничениями зала (сколько рядов, сколько мест в каждом ряду).
- **Статусы места (внутренние)**:
  - **Свободно**: место доступно.
  - **Бронь**: место выбрано покупателем, но еще не оплачено.
  - **Оплачено**: место ранее было в брони, по нему внесена оплата (возможна частичная оплата брони).
  - **Резерв**: место занято под гостей, купить нельзя.
- **Можно забронировать / нельзя забронировать (для карты зала)**:
  - **Можно** = Свободно
  - **Нельзя** = Бронь или Оплачено или Резерв
- **Бронь**: набор мест, закрепленных за конкретным покупателем (VK-аккаунт), с указанием билетера, который оформил бронь.
- **Чек**: сообщение в VK с подтверждением оплаты (пересылается билетером в бота).
- **Оплата**: запись о чеке + привязка к брони + количество оплаченных мест (частично/полностью).
- **Расход**: запись о выводе денег на нужды концерта, уменьшающая баланс.
- **Чекап (финансовая сверка)**: отметка “проверено до момента времени T”; интерфейс по умолчанию показывает изменения после последнего чекапа.

## 3) Ограничения и правила (важные)

- **Событие одно**, площадка и расстановка мест **одна**.
- **Цена фиксированная**: одинакова для любого места и любого количества.
- **Бронь не сгорает** автоматически.
- **Оплату может подтвердить только покупатель, который бронировал**:
  - чек должен быть отправлен “нужным” VK-аккаунтом (который привязан к брони),
  - сценарии “один VK оплатил за другого” не поддерживаются.
- **Карта зала**:
  - статичная страница,
  - показывается только 2 состояния: можно/нельзя забронировать,
  - без кликов/выбора/попапов; чтобы увидеть номер — пользователь приближает (zoom).
- **Конфликты / консистентность**:
  - нельзя забронировать или зарезервировать занятое (Бронь/Оплачено/Резерв),
  - нельзя занять Резерв,
  - частичная оплата возможна (часть мест в брони становится “Оплачено”, остальное остается “Бронь”),
  - операции изменения мест должны быть **атомарными** (чтобы два билетера не заняли одно место).

## 4) Роли и доступы

### 4.1 Роли

- **Билетер**
  - доступ: VK-бот + веб-страница “День концерта”
  - операции: создавать/редактировать брони, отмечать оплаты по чекам, управлять резервом
- **Админ**
  - доступ: весь веб (финансы, чекапы, история действий с фильтрами)
  - операции повышенного риска: отмена оплат/откат оплаченных мест, просмотр/фильтрация полной истории действий

### 4.2 Матрица прав (высокоуровнево)

| Операция | Билетер | Админ |
|---|---:|---:|

## 5) Интерфейсы

### 5.1 Публичная веб-страница “Карта зала”

**Цель**: дать покупателю визуал зала (без покупки), где видно только “можно/нельзя”.

- **Входные данные**: заранее сверстанная картинка/схема (например, SVG/PNG) с подписанными местами.
- **Отображение**:
  - места “можно” выделены одним цветом,
  - места “нельзя” выделены другим цветом,
  - без интерактива (без кликов, подсказок, списка выбранных мест).
- **Навигация**:
  - должно быть удобно приближать/отдалять на телефоне/ПК (встроенный zoom страницы или масштабируемый SVG/контейнер).

### 5.2 Веб-страница “День концерта” (для билетеров и админа)

**Цель**: быстро находить людей и их места в день мероприятия, печатать таблицу.

Функции:
- таблица: **отсортированный по алфавиту список по именам VK** (по умолчанию) с местами и статусом **оплачено / не оплачено**
  - обязательные колонки:
    - имя покупателя (как в VK)
    - ряд (отдельная колонка)
    - места (отдельная колонка; допускаются диапазоны, например `1-3,5,8-10`)
    - статус оплаты: **оплачено / не оплачено**
  - опциональные колонки (если будет удобно):
    - ссылка на VK
    - кто продал (билетер)
    - время брони (для сортировки)
    - служебные поля (ID брони)
- поиск (в веб-версии):
  - по имени
  - по ряду/месту (включая поиск по диапазонам мест)
- сортировка (переключаемая):
  - по алфавиту имен (по умолчанию)
  - по времени брони
  - по рядам и местам в рядах (сначала ряд ↑, затем место ↑)
- печать:
  - “верстка для печати” (CSS print)
  - кнопка “Печать” (без генерации файла обязательно; PDF опционально через печать браузера)
  - требования к печати:
    - адекватная ширина колонок (без обрезаний ключевых полей: имя, места)
    - минимум лишнего UI (скрывать поля ввода/кнопки/навигацию в режиме печати)
    - возможность печатать в черно-белом виде (статусы — текстом/метками, не только цветом)

### 5.3 Веб-интерфейс админа (финансы и аудит)

Разделы:
- **Финансы**
  - суммы:
    - сумма по **оплаченным** местам = (кол-во оплаченных мест) × цена
    - сумма по **забронированным** местам = (кол-во мест в статусе “Бронь”) × цена
    - текущий **баланс** = сумма оплат − сумма расходов
  - список оплат (чеков) с деталями:
    - дата чека (дата сообщения)
    - покупатель (VK)
    - к какой брони привязано
    - сколько мест оплачено (и/или какие места — если поддержим)
    - ссылка на сообщение с чеком
    - кто отметил оплату (билетер)
  - список неоплаченных броней:
    - брони, где есть места “Бронь”
    - возраст брони (сколько дней)
    - кто продал (билетер)
  - расходы:
    - список расходов (дата, сумма, комментарий/категория, кто внес)
    - добавить расход (уменьшает баланс)
  - **Чекап “проверено”**:
    - кнопка “Отметить проверено”
    - после чекапа **не скрывать** проверенные записи полностью
    - проверенные записи должны быть **свернуты в аккордеон** (например, “Проверено ранее”), а новые — отображаться сверху
- **Аудит/история действий**
  - список всех действий пользователей в системе
  - фильтры:
    - по типу действия (детализация будет уточнена позже)
    - по пользователю (билетер/админ)
    - по периоду времени
    - по покупателю (VK)
    - по брони (ID/покупатель)
  - просмотр деталей события (payload)

## 6) Операции (что система должна уметь)

### 6.1 Операции с бронями и местами

- Создать бронь на покупателя (через VK-бот по пересланному сообщению).
- Добавить места в бронь:
  - валидировать существование ряда/места по ограничениям зала,
  - валидировать, что место свободно (не Бронь/Оплачено/Резерв),
  - добавлять сразу пачкой.
- Убрать места из брони (частично).
- Удалить бронь целиком (с освобождением мест).
- Просмотр текущей брони покупателя (места и их статусы).

### 6.2 Операции с резервом

- Добавить места в резерв (билетер или админ).
- Убрать места из резерва (билетер или админ).
- Резерв нельзя накладывать на занятое место; бронь нельзя накладывать на резерв.

### 6.3 Операции с оплатами

- Привязать чек к покупателю и к конкретной брони (через пересланное сообщение в VK-бот).
- Поддержать **частичную оплату**:
  - бот должен спросить, сколько мест из забронированных оплачено по этому чеку,
  - система переводит соответствующее количество мест из “Бронь” в “Оплачено”.
- Сохранять по каждой оплате:
  - ссылку на сообщение (чек),
  - дату сообщения (дата оплаты),
  - кто отметил оплату,
  - сколько мест оплачено.
- **Отмена/откат оплаты** — только админ:
  - откат “Оплачено” → “Бронь” (или в “Свободно”, если бронь удалена — уточнить при детализации).
  - обязательное логирование причины и ссылки на исходную оплату (чек).

### 6.3.1 Частичная оплата: как выбирать, какие места стали “Оплачено”

В текущем UX бот спрашивает только **количество** мест, без перечисления.

- Базовое правило по умолчанию: помечать “Оплачено” места в брони в стабильном порядке:
  - сначала по возрастанию ряда, затем по возрастанию номера места,
  - только среди мест в статусе “Бронь”.
- Альтернатива (если понадобится точность): бот может дополнительно спрашивать список мест (как при бронировании).

### 6.4 Операции с финансами и расходами (админ)

- Расчет агрегатов (см. раздел 5.3).
- Добавить расход (уменьшает баланс).
- Редактировать/удалять расход (только админ; обязательно логировать).
- Чекап “проверено до T”:
  - фиксирует момент времени,
  - интерфейс по умолчанию показывает новые записи после T.

### 6.4.1 Корректировки финансов (админ)

Чтобы суммы в отчетах были воспроизводимы:
- отмена оплаты должна либо:
  - создавать “обратную” запись (корректировку), либо
  - помечать исходную оплату отмененной с указанием причины/кто/когда,
  - при этом агрегаты (оплачено/баланс) пересчитываются с учетом отмены.

> TODO: выбрать подход “корректировка-операция” vs “статус оплаты: отменена” при реализации.

### 6.5 Общие требования к логированию (все операции)

- Любая операция, меняющая состояние мест/броней/оплат/расходов/резерва, должна создавать запись в **полном логе действий**.
- Должно быть видно:
  - кто сделал действие (билетер/админ),
  - когда,
  - что изменилось (до/после или эквивалент в payload),
  - к какой сущности относится (бронь/оплата/расход/резерв/покупатель).

## 7) Флоу взаимодействий (пошагово)

### 7.1 VK-бот: создание брони по пересланному сообщению

**Триггер**: билетер пересылает боту сообщение от покупателя.

Шаги:
1. Бот определяет VK-аккаунт автора исходного сообщения (покупателя) и сохраняет/обновляет его имя + ссылку.
2. Бот проверяет, есть ли у покупателя активная бронь:
   - если нет → создает бронь и пишет “Бронь создана”.
   - если есть → предлагает:
     - продолжить добавлять места в текущую бронь
     - или создать новую бронь (если допустимо; по умолчанию лучше одна активная бронь — уточнить позже).
3. Бот предлагает перейти к вводу мест: “Введите ряд”.

### 7.2 VK-бот: добавление мест (ряд → свободные диапазоны → места)

**Триггер**: билетер вводит номер ряда.

Шаги:
1. Бот валидирует ряд (существует по ограничениям зала).
2. Бот отвечает сообщением со свободными диапазонами мест в этом ряду, например:
   - “Свободно: 1-4, 6-9, 12-15”
   - и подсказка формата: “Введите места: `1-3,6,12-13`”
3. Билетер вводит места списком/диапазонами.
4. Бот парсит ввод, валидирует все места (существование, свобода).
5. Если ввод распарсен и места валидны:
   - бот **не переспрашивает подтверждение**,
   - фиксирует бронь (атомарно занимает места).
6. После успешной фиксации бот отправляет **два сообщения** билетеру:
   - (1) **готовый текст-скрипт** для покупателя (копировать/вставить), например:
     - “Ваши места: Ряд X, места A,B,C забронированы за вами. Оплачивайте и пришлите чек…”
   - (2) **сообщение со ссылкой на чат/диалог покупателя**, куда этот скрипт нужно отправить.

Примечание:
- Проверка корректности списка мест перекладывается на покупателя (билетер отправляет скрипт, покупатель видит, что именно забронировано).

### 7.2.1 VK-бот: формат ввода мест (парсер)

Поддерживаемые варианты:
- список: `1,2,5`
- диапазоны: `1-5`
- смешанный: `1-3,5,8-10`
- пробелы допускаются и игнорируются: `1-3, 5, 8-10`

Правила:
- дублей быть не должно (бот должен убрать дубли или сообщить об ошибке — выбрать при реализации)
- ввод должен валидироваться на:
  - целые положительные числа
  - границы диапазонов (левая ≤ правая)
  - существование мест в ряду по ограничениям зала
  - текущую доступность места (свободно / в резерве / в брони / оплачено)

Ошибки (пример ожиданий):
- невалидный формат → сообщение с примером корректного ввода
- места заняты/в резерве → перечислить конфликтные места и предложить повторить ввод
- часть мест валидна, часть нет → по умолчанию **не** бронировать ничего (атомарность ввода), а попросить исправить

### 7.3 VK-бот: добавление мест в несколько рядов

После успешной брони по ряду бот предлагает:
- “Введите следующий ряд” или команда “Готово”.

### 7.4 VK-бот: снять бронь / убрать места

Поддерживаемые варианты:
- Удалить бронь целиком (освободить все места брони).
- Удалить конкретные места:
  - выбор ряда → ввод мест форматом списка/диапазонов → удалить только их.

Бот должен показывать краткую сводку брони после изменения.

### 7.4.1 VK-бот: быстрые команды (черновик)

> Это черновой список команд; финальный список и названия уточним при реализации.

- “Новая бронь” / пересылка сообщения покупателя → создать/выбрать бронь
- “Добавить места” → сценарий ряд → места
- “Убрать места” → сценарий ряд → места
- “Удалить бронь” → удалить бронь целиком
- “Показать бронь” → сводка по активной брони покупателя
- “Резерв” → добавить/убрать резерв
- пересылка чека → сценарий оплаты

### 7.5 VK-бот: отметить оплату по чеку (частичная оплата)

**Триггер**: билетер пересылает боту сообщение с чеком от покупателя.

Шаги:
1. Бот определяет VK-аккаунт автора чека (покупателя).
2. Бот находит активную бронь покупателя.
   - если броней несколько: предлагает выбрать бронь (минимум по списку мест/дате создания).
   - если брони нет: сообщает ошибку и предлагает сценарий “сначала создать бронь”.
3. Бот показывает, сколько мест сейчас в брони и сколько из них уже оплачено.
4. Бот задает вопрос: “Сколько мест оплачено по этому чеку?” (число от 1 до кол-ва неоплаченных мест).
5. Бот создает запись оплаты:
   - ссылка на сообщение (чек),
   - дата сообщения,
   - кто отметил (билетер),
   - количество мест.
6. Бот переводит указанное количество мест из “Бронь” → “Оплачено”.
7. Бот отправляет итог:
   - “Оплата учтена: N мест. В брони осталось неоплачено: M мест.”

Ошибки/валидации:
- если пользователь по чеку не найден/не совпадает с покупателем брони → отказ, с пояснением
- если оплаченных мест указано больше, чем мест в статусе “Бронь” → отказ и запрос корректного числа

### 7.6 VK-бот: управление резервом

Команды/сценарий:
1. Билетер вводит команду “Резерв”.
2. Бот спрашивает: добавить или убрать.
3. Бот принимает ввод мест (ряд → места) как в сценарии брони.
4. Бот валидирует:
   - место свободно для добавления в резерв,
   - место в резерве для снятия резерва.
5. Бот применяет изменения и пишет результат.

### 7.7 Веб (админ): финансы и чекапы

**Финансы**:
- таблица оплат (чеков), фильтр по периоду
- агрегаты:
  - оплачено (в рублях)
  - забронировано (в рублях)
  - баланс (в рублях)
- расходы:
  - добавить расход (дата, сумма, комментарий/категория)
  - баланс уменьшается

**Чекап**:
- кнопка “Проверено”
- после нажатия:
  - фиксируется момент T
  - записи до T не скрываются, а переносятся под **аккордеон “Проверено ранее”**
  - новые записи после T показываются сверху

### 7.8 Веб (день концерта): поиск и печать

- быстрый поиск (имя/VK/ряд/место)
- печать таблицы (print CSS)

## 9) Правила конфликтов и атомарность (детализация)

Требования к поведению при одновременных действиях нескольких билетеров:
- операции “добавить места в бронь” и “добавить в резерв” должны выполняться атомарно:
  - либо заняты все запрошенные места,
  - либо не занято ни одно (и бот сообщает причину).
- если два билетера одновременно пытаются занять одно и то же место:
  - выигрывает тот, чья транзакция/операция завершилась первой,
  - второй получает ответ “место уже занято” с перечнем конфликтов.

## 11) Переходы статусов мест (разрешенные/запрещенные)

Ниже описаны ожидаемые переходы статусов для одного места.

### 11.1 Разрешенные переходы

- **Свободно → Бронь**: билетер добавил место в бронь.
- **Бронь → Свободно**: билетер убрал место из брони или удалил бронь.
- **Свободно → Резерв**: билетер/админ добавил место в резерв.
- **Резерв → Свободно**: билетер/админ снял резерв.
- **Бронь → Оплачено**: билетер привязал чек и отметил оплату (частично/полностью).
- **Оплачено → Бронь**: админ отменил оплату (откат в бронь).
- **Оплачено → Свободно**: админ удалил опплату и бронь.

### 11.2 Запрещенные переходы (по умолчанию)

- **Резерв → Бронь** (сначала снять резерв).
- **Резерв → Оплачено** (сначала снять резерв, затем бронь/оплата — если вообще нужно; по умолчанию не поддерживается).
- **Бронь → Резерв** (сначала убрать из брони).
- **Оплачено → Резерв** (не поддерживается).
- **Свободно → Оплачено** (оплата возможна только для ранее забронированных мест).

## 12) Уведомления по должникам (детализация требований)

### 12.1 Кому и что отправляем

- Получатели: **все билетеры**.
- Содержимое: каждый билетер получает **только свои** брони-должники (по полю “кто продал/создал бронь”).

### 12.2 Когда считать бронь “должником”

Бронь считается “должником”, если одновременно:
- в брони есть хотя бы одно место со статусом **Бронь** (не оплачено),
- прошло ≥ 7 дней с момента **последнего действия** по брони (последнего изменения брони/мест/оплат по этой брони).

Примечание:
- “последнее действие” включает любые операции, меняющие бронь: добавление/удаление мест, удаление брони, отметка оплаты/частичной оплаты, отмена оплаты (админ).

### 12.3 Когда и как часто отправлять

- 1 раз в трое суток вечером (время будет задано позже).
- В сообщении должен быть:
  - общий итог (сколько броней-должников, сколько неоплаченных мест),
  - список броней (покупатель + ссылка VK + места + как долго висит бронь).

### 12.4 Логирование уведомлений

- Отправка напоминаний должна логироваться (как системное событие), чтобы можно было понять:
  - кому и когда отправляли,
  - какой список/сколько элементов было в подборке.
